# 提示词迭代方法与评价标准

本文规定提示词迭代如何开展、怎样判断改善，以及最终期望达到什么效果。它是长期规范，不记录每个版本的测试过程。

版本改动和测试结论单独写入[迭代台账](prompt-iteration-log.md)，完整证据保留在各版本验证报告。消息结构、配置格式和代码入口见[提示词技术说明](prompting.md)。

## 一、最终期望的效果

目标是让双方都像有目标、会判断、能交流的阿瓦隆玩家，而不是让好人固定获胜、刺客总能猜中，或每位玩家每轮都完成规定动作。

| 方面 | 期望表现 | 不应变成 |
| --- | --- | --- |
| 合法视角 | 只使用本人合法信息和当时已公开事件，区分私有判断与公开事实 | 全知视角、匿名任务牌自证、泄露候选关系 |
| 事实与推理 | 历史引用准确；能使用任务约束；策略假设始终保留前提 | 用旧猜测当事实、把成功当验人、从下界凭空推出上界 |
| 好人决策 | 优先提高任务成功机会，能纠偏并兼顾梅林保护 | 为查清责任反复带嫌疑上车，或因一辆车含未知位就机械否决 |
| 坏人决策 | 伪装服务破坏车位、失败票或有依据的刺杀机会 | 为保持低调全程替好人推进，或被强制每车反对 |
| 角色差异 | 梅林兼顾任务与隐藏，派西维尔辨别并保护，忠臣独立推理，坏人合理误导 | 只有梅林会选车，其他人只复述规则；奥伯伦假装互认队友 |
| 发言 | 信息少时自然简短；有分歧时说最影响判断的一点；有理由才追问 | 人人长篇复盘、换词复读，或为了不重复而硬造争议 |
| 连贯性 | 发言、组队、投票和个人记录的变化有依据，后续可公开解释 | 为坚持旧话放弃阵营目标，或无新依据地翻转决定性立场 |
| 对局体验 | 双方能产生真实压力，正确方案可以来自不同玩家，身份仍有不确定性 | 固定脚本、预设胜者、靠故意选错车制造悬念 |

玩家可以判断错误、保持分歧或使用诈身份。评价重点是判断依据与阵营目标是否合理，不是是否与最终身份答案完全相同。

## 二、每轮迭代怎样开展

### 1. 从可复核的问题开始

先看完整发言、组队、投票、任务和刺杀记录，再检查相关决策摘要。按问题发生时的合法视角评价，不借最终身份真相要求普通玩家提前知道答案。

每个问题至少写清：出现在哪局、哪轮或哪条事件；当时知道什么；哪里不成立或没有推进决策；造成什么实际影响。区分以下类型：

- 事实错误：引用错队长、成员、票型或发言先后。
- 推理错误：前提不足以支持结论，或推断与已有约束矛盾。
- 策略问题：推理可以成立，但行动没有合理服务阵营目标。
- 表达问题：没有新内容却重复，或理由没有说到影响当前选择的分歧。
- 验证问题：样本未覆盖目标场景、版本未加载、上下文截断或请求错误。

坏人故意曲解真实记录、诈身份或给出有利于自己的片面解释，不自动算作其真实推理失败。结合私下依据判断它是有目的的误导，还是自己也相信了错误结论；不能把坏人按最优好人标准评分。

### 2. 选一个主要目标，先写预期行为

每轮围绕一个主要问题，必要时处理直接相关的冲突。先写清：

```text
问题证据：
可能原因：
本轮改动：
预期看到的行为：
可能受影响的已有能力：
验证场景与判定方式：
```

预期应可观察。例如“赛点车缺少可控破坏点时，坏人能比较否决与后续车位，并在有利时实际争取换车”，而不是“坏人更积极”或“坏人必须投反对”。

同一问题连续未改善时，重新检查原因、提示词冲突和验证方式，不只增加禁词、例句或“必须”条款。单纯改写术语不算完成行为目标。

### 3. 定位并修改最小范围

- 通用判断与信息边界改系统正文；身份差异改对应角色；具体动作改行动正文。
- 优先重写或删除冲突要求，不把新规则不断叠在相反的旧要求上。
- 不为某个种子、座位号或一次刺杀答案写特例，不强制故意选错车来隐藏身份。
- 行为变化更新 `config.example/prompt_templates.json` 的版本，保留已有未提交修改。
- 若需要改上下文、输出契约、规则或评估器，将其明确列为额外改动，不伪装成纯提示词调整。

默认正文位于 `config.example/prompts/`。不在提示词文件中夹带迭代说明，过程写入台账。

### 4. 先完成相称的基础检查

提示词正文调整优先运行相关测试并核对配置加载、角色信息边界、JSON 契约和差异：

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests/ai -v
git diff --check
```

通过这些检查只说明配置与接口未发现回归，不证明模型决策质量达标。不为复述一句文案而新增测试；修改消息结构、契约或规则时，再按实际影响扩大检查。

仅整理文档时检查内容、路径、链接和命令，不开真实模型对局，也不重复运行完整测试。

### 5. 固定测试条件，再运行对局

每次记录提示词版本、模型配置ID、模型名、推理档位、玩家数、机制、进阶策略开关、随机种子、AI代打范围，以及超时等进程内覆盖值。

同种子可固定初始身份和席位，但模型输出及后续历史仍会变化，不称为严格控制的 A/B 测试。跨种子用于观察角色分布和压力场景，不能只挑获胜或表现好的种子。

使用独立数据库、新进程和正常决策链路验证；保持后端唯一规则裁判。不要同时启动多个执行器推进同一数据库中的同一局，不通过屏幕点击测试。

测试过程中不更改提示词、不向模型补充复盘结论、未来事件或其他玩家的隐藏信息。请求失败时记录原错误，恢复原局；若只调整超时，明确记下，不偷偷换模型或推理档位。

后续测试应保存该版本的提示词正文或可重建快照。版本号和 `stable_prefix_hash` 不能替代全部文本快照：哈希只核对稳定前缀，私有角色正文和临时行动说明也可能影响结果。

### 6. 复盘并给出有限结论

完整局检查事件重放、终局和有效决策版本，再按本轮预期逐项判断。针对同一问题的检查通过后，不在没有新改动、失败或疑点时机械重跑。

结论使用“改善证据明确、部分改善、未改善、回退、未覆盖”等表述，并说明证据范围。单局可以证明出现过某种行为或反例，不能证明稳定胜率、刺杀命中率或所有角色都已改善。

继续验证时覆盖已暴露问题的场景和不同身份分布，提前说明为什么需要新样本，而不是不断开局筛选好结果。候选关系、第四轮门槛、失败归因、改票、刺杀等未出现的分支标为未覆盖。

## 三、评价标准

### 1. 先核对基本边界

以下问题不能被胜利、短发言或高缓存命中率抵消：

- 使用未授权的隐藏信息，或将私有候选、任务牌当成公开证明。
- 改写已经公开的事件，引用不存在的票型、组队或原话。
- 将可以构造反例的结论说成“必成功、必含坏人、至多若干坏人”等硬结论，并据此决策。
- 非法动作或输出导致无法完成决策。区分模型初始错误、重试恢复和最终暂停，不只看最终是否跑完。

发现这些问题，记录具体反例、影响及归属层：模型推理、提示词冲突、信息投影、契约或运行过程。当前文件可以保留为待改候选，但不能因此标成“质量通过版”。

### 2. 核对推理：前提必须一直保留

评价时区分四层依据：

| 依据 | 示例 | 能支持什么 |
| --- | --- | --- |
| 公开约束 | 某车出现两张失败票 | 全桌可用的车内至少两坏 |
| 自知身份 | 我是好人，且在失败车中 | 本人可用的剩余成员嫌疑约束；他人不必将此前提视为已证实 |
| 合法私有信息 | 梅林所见坏人、候选或湖女结果 | 本人的决策依据，不自动成为公开结论 |
| 策略假设 | 若坏人会争取立即获胜，可能不会藏牌 | 带条件的软判断，不能写入后续记录后变成确定事实 |

硬结论应经反例核对：是否存在另一组与当时合法信息相容的身份分布，使结论不成立？有反例就不能称为保证；实际选车偶然正确也不能修复错误证明。

可以人工构造反例或离线枚举，但不能拿最终真实身份反向裁判玩家当时应知道什么。失败票提供坏人数下界；成功票、未达到失败门槛、某人没出失败，都不直接提供坏人数上界。投票与发言可帮助判断，不直接限定真实阵营。

### 3. 按身份目标评价策略

| 身份 | 重点检查 |
| --- | --- |
| 忠臣及普通好人 | 能否使用公开约束和自己的身份前提，比较低风险方案，而不是只追责、只测试或只跟随 |
| 梅林 | 任务方向与整局暴露风险是否兼顾；公开理由是否有依据；不以一次混入坏人或故意错误代替隐藏 |
| 派西维尔 | 是否根据实际车位、风险和纠偏更新候选判断，保护而不公开绑定两名候选，不按固定轮次强行开身份线 |
| 互认坏人 | 隐藏是否换来破坏位置或刺杀信息；支持、否决、切割、藏牌和失败是否服务可解释的阵营收益 |
| 奥伯伦 | 是否在不互认的前提下行动，争取自己可影响的位置，不假装知道同伴或无依据排除其他坏人 |
| 刺客 | 是否比较全部合理目标，区分公开推理、自知好人的自荐与难以解释的精准，不只按上车、带队或发言先后排序 |

刺杀猜错、好人否掉好车或坏人支持好车，不自动是策略错误；检查当时依据、替代选择和局势收益。不能以增加反对票、追问、身份动作或诈身份次数作为优化目标。

### 4. 按信息增量评价表达与连贯性

判断一段话是否增加了新约束、关键分歧、合理建议、立场变化解释，或者有必要的支持。没有新增信息时一句认同是有效发言，不要求人人说出不同理由。

复读按语义判断：将“责任”换成“样本”，再换成“有限支持、连续性、先看结果”，如果没有改变判断依据，仍是同一问题。纠错、首次解释重要门槛或必要重申立场，不应仅因用了相同词就算重复。

改票可以合理发生。检查是否有后续信息或局势依据、私下摘要是否解释，以及下一次有发言机会时是否补充可公开的原因；对方已经无法回应的问题，不应被当成等待回答的条件票。

### 5. 量化指标只作辅助

每局至少保留发言、投票、组队、有效决策、错误和任务结果数量，以及本轮目标对应的事件证据。表达问题可辅助记录平均长度、不超过50字符的数量和语义重复样例。

“50字符”只是当前历史记录的描述口径，不是每段发言的硬上限或通过线。词频下降不等于推理改善，长度下降不等于没有复读，任务成功也不代表最终获胜。

token、时延、缓存和错误恢复用于判断运行代价，不替代玩法质量。若未记录某项指标，明确未测，不补写估计值。

## 四、旧评估器与历史标准

`scripts/prompt_log_evaluator.py` 保留了较早阶段的启发式质量门，其中“缺少身份争夺、缺少候选压力、私下候选没有公开动作”等要求，与当前允许低调和简短认同的目标不完全一致。

它可以提供事实错误、泄露或词频等诊断线索，但不能直接作为当前总体验收标准。先检查输入结构和误报，再引用结果；完整复盘导出与旧采样格式不同，不能把原始导出直接当成旧格式使用。

本规范不表示评估器代码已经同步更新，也不自动触发真实模型测试或子代理审阅。委派遵循仓库的用户授权与读写边界要求。

## 五、如何记录与收尾

- 本文只维护长期方法、标准和目标，不不断追加某版本的对局细节。
- [迭代台账](prompt-iteration-log.md)记录日期、版本、问题、改动假设、样本、证据结论、未解决项和下一步。
- `prompt-vNN-verification.md` 保存该版本的详细复盘，后来发现新问题时追加更正，不把旧的未通过结论覆盖成成功。
- 数据库、完整私有审计、模型配置和日志只保留本地；提交文档不携带真实 API Key。
- 清理无后续用途的临时脚本，保留必要的验证证据；记录本次是否重启常驻后端，区分文件版本与实际加载版本。

当前已知问题和下一轮优先级以台账为准；没有实际修改或测试的计划，不记成已完成迭代。
