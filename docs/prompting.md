# AI 提示词规范与功能说明

本文档总结 SoloAvalon 当前 AI 提示词的设计边界、配置能力和维护约定。目标是让模型像合法玩家一样参与讨论和决策，同时避免把调试信息、配置元信息或隐藏真相泄露给模型。

## 核心原则

- 只使用当前玩家合法可见的信息，包括自己的身份视角、公开玩家列表、公开发言、公开投票结果、任务结果和当前可执行动作。
- 不向模型发送原始 `private_view`、`public_state`、`recent_public_events`、`legal_actions` 等 JSON 上下文字段。
- 不向模型发送提示词版本号、配置键名、默认开关、推荐身份组合等元信息。
- 前缀内容尽量稳定，便于模型服务端缓存；动态信息集中在玩家视角、活动日志和本次行动中。
- 后端是唯一规则裁判。模型只能提出动作意图，合法性由后端校验。

## 配置文件

可提交的提示词配置位于：

```text
config.example/prompt_templates.json
```

本地可通过环境变量覆盖：

```powershell
$env:SOLOAVALON_PROMPT_CONFIG="E:\path\to\prompt_templates.json"
```

真实模型配置仍位于被 git 忽略的 `config/llm_profiles.json`，不要把真实 API Key 或供应商配置写入提示词配置。

## 发送给模型的结构

当前模型消息分为五段：

```text
【系统】
【本局配置】

【你的视角】

【动作 JSON 格式声明】

【活动日志】

【本次行动】
```

`【系统】` 和 `【本局配置】` 放在 system message 中，用于提供稳定规则背景。`【你的视角】`、`【动作 JSON 格式声明】`、`【活动日志】`、`【本次行动】` 分别作为 user message 发送。

### 拼接流程

提示词从游戏状态到模型请求的调用链如下：

1. `GameService` 在自动推进 AI 行动或真人托管 AI 行动时调用 `AiPlayer`。
2. `AiPlayer._decide()` 调用 `ContextBuilder.build()`，把 `GameState`、当前玩家、当前阶段和公开事件整理成 `AiContext`。
3. `ContextBuilder.build()` 生成两类上下文：
   - `stable_prefix`：稳定前缀，用于 system message。
   - 动态上下文：玩家私有视角、公开状态、近期公开事件和当前合法动作。
4. `PromptBuilder.build_messages()` 把 `AiContext` 渲染成 OpenAI-compatible Chat Completions 的 `messages`。
5. `LlmProvider.chat_completion()` 把 `messages` 放入请求体并发送给模型接口。

当前最终消息结构是：

```python
[
    {"role": "system", "content": context.stable_prefix},
    {"role": "user", "content": "【你的视角】..."},
    {"role": "user", "content": "【动作 JSON 格式声明】..."},
    {"role": "user", "content": "【活动日志】..."},
    {"role": "user", "content": "【本次行动】..."},
]
```

`messages[0]` 必须保持为 `system = context.stable_prefix`。后续 `user` messages 的顺序固定为玩家视角、动作 JSON 格式声明、活动日志、本次行动。

`dynamic_private_suffix` 是 `ContextBuilder` 生成的结构化上下文快照，主要用于测试、审计和确认隐藏信息边界；当前不会直接发给模型。最终发给模型的是 `PromptBuilder` 渲染后的自然语言段落，避免暴露 `private_view`、`public_state`、`recent_public_events`、`legal_actions` 等原始字段名。

### 系统与本局配置

包含：

- 真实桌游发言风格：积极争取上车、质疑车队、表达上车/下车意愿。
- 发言/投票自洽：玩家需要承接自己上一轮公开立场，后续投票应能被公开发言解释；若改票或改变组队方向，需要说明新信息、新压力或身份叙事变化。
- 票型引用核对：`prompt.v11` 要求模型引用他人历史投票、组队、任务成员或发言原话前，必须先在活动日志中核对具体记录；没有把握时应改成追问，避免把反对说成赞成或捏造未发生的矛盾。
- 套话降噪：避免全桌反复使用通用安全套话，也避免换成同义安全句；同一轮尽量从不同矛盾、车位压力或身份叙事切入。`prompt.v19` 减少在 prompt 里完整复述禁句，改为提供正向替代表达，例如带谁、暂时不带谁、炸了先问谁、谁这轮别被打死，降低模型照抄负面示例的概率。
- 局势目标判断：每次行动先判断本轮要争取车位、要求谁下车、保护谁、施压谁，或制造/拆解哪条叙事。
- 话语权动作：围绕车队、票型、任务压力、他人身份叙事和公开矛盾主动推进讨论。
- 条件性身份扮演：身份宣称、跳身份、反跳、抢身份、挡刀和诈身份是可选公开发言策略，不是固定动作。
- 身份叙事债：`prompt.v12` 参考真人局里“不要无脑跳派，但要争候选解释权”的打法。一旦场上出现派西维尔、梅林候选、保护线或对跳，玩家不能只说“先观察”；公开发言或组队说明要回答自己站哪条候选线、拆哪条候选线、反跳谁、逼问谁在保护谁，或为什么暂时替某条线挡一下。`prompt.v13` 进一步补充安全动作菜单：软保一人、拆一条保护关系、逼问某人为什么急着排/保某人、把候选压力转成车位压力；优先点单人或行为线，不公开绑定两个真实候选。`prompt.v14` 把动作改成更能直接说出口的短句，例如“玩家X一直替玩家Y卸压”“玩家X急着排玩家Y”“我先偏保玩家X这轮上车”“这不像普通好人互相评价”。`prompt.v15` 继续要求用自己的话完成动作，避免整局复读示例句，并压制“责任链清晰”“这条线我先记着”“后续再看”等新模板。`prompt.v16` 要求当私下候选关系影响本轮态度时，公开必须落一个不泄露身份的动作，不能只说车队结构。`prompt.v17` 针对 DS 小样本里“这条线我先保着”这种空泛落点，要求公开动作必须点出至少一名玩家或一个具体行为关系。`prompt.v19` 根据真人派西维尔资料补充“不要报拇指”的边界：真派不应把两名候选直接摊开，而应通过车位、投票、候选派票和对跳反应收集信息；有人抢跳派西维尔时，先判断是候选挡刀、坏人抢解释权还是忠臣挡刀，再决定是否反跳或拆线。
- 身份姿态选择：每次公开发言前先决定自己要扮演普通好人、可信上车位、强势推理位、保护位、反跳位、挡刀位、假身份试探，还是有意低调隐藏。
- 组队可解释性：组队理由必须能从公开发言、票型、任务结果、上轮车队结构、场上共识或试车压力中推出；当真实判断与公开证据不匹配时，应优先选择公开上自然且可辩护的车，避免暴露私有视角的最优车。
- 派西维尔话语权：派西维尔是有利身份姿态，也是一种公共话语权资源。非派西维尔在首轮争车位、关键车队前、有人跳身份、票型分裂、任务失败归责、自己被边缘化或需要保护疑似梅林时，都要评估是否短暂借派西维尔姿态，暗示候选判断、保护或转移候选、反跳假派西维尔或质疑候选关系；公开理由必须来自公开信息，连续使用或局势不需要时应退回普通好人/保护位。
- 身份叙事响应：当公开记录已经出现梅林候选、派西维尔姿态、保护/挡刀话术或有人质疑假派西维尔时，发言不能只绕开身份叙事；至少要用一句话选择扮演、反跳、质疑、保护或挡刀，并把它和车队/票型压力连起来。拒绝逼身份也必须表现为保护位或挡刀位话术，而不是简单说信息少、太早、先观察。假扮派西维尔不能凭空硬报未公开候选名单，应优先使用可进可退的保护、候选解释或挡刀话术。
- 公开姿态落地：身份姿态必须体现在公开发言里，不能只写在私下理由中；如果选择保护位、挡刀位或派西维尔姿态，公开发言必须明确保护/拆解至少一条具体叙事。
- 姿态不是身份标签：不要公开自称“我是保护位”“我是挡刀位”。保护位/挡刀位应通过保人、拆线、挡话和换车诉求表现出来。
- 半露视角边界：佯装暴露身份视角时要半真半假、可否认，可以说“我这边更认这个方向”“我偏保玩家X这轮上车”“这条保护关系不自然”，不要说成系统视角、验人结果、真实阵营或不可质疑的确定身份。公开发言也不能说“我投了成功”“我没出失败票”来证明自己，应改成“从我的立场我不认这张锅”“同车其他人需要解释”。
- 私有信息降噪：拥有合法私有信息的身份也不能把最优答案直接翻译成连续精准的组队、投票和发言；特别是梅林要同时评估任务胜率和刺杀暴露风险，避免让车队结果本身暴露私有视角。`prompt.v10` 进一步要求梅林在连续两次精准避坏或反对含坏车后，非决胜行动优先降低可读性，例如跟随公开共识、保留公开可信但私下有风险的位置、只投票不强带队，或让别人先提出正确方向。
- 桌面话术降标签化：公开发言少用“保护位”“派西维尔视角”“验人”等身份标签，多用“我偏保玩家X”“玩家X急着排玩家Y”“玩家X一直替玩家Y卸压”“从我视角看”“按当前任务结果”“我暂时只能怀疑”“队长解释一下为什么这样组”等动作和限定词。
- 推理限定：除非规则公开结算已经证明，否则不要说“确定”“铁好”“铁坏”“验出来”。失败任务后应说“从我视角这几个人需要解释”，而不是把嫌疑二选一说成全桌确定事实。
- 其他玩家的自称身份只是待验证信息，需要结合公开发言、组队、投票和任务结果判断真假。
- 玩家人数。
- 好人/坏人人数。
- 每轮任务人数。
- 每轮任务失败所需失败票数。
- 本局实际身份和身份机制说明。
- 已启用的扩展机制，例如湖中仙女；启用与否来自当前对局状态，而不是 prompt 配置的默认值。

不包含：

- `Prompt 模板版本`。
- `推荐身份组合`。
- 配置开关名称，例如 `enabled`。
- 默认启用人数、默认不加入推荐组合等配置管理说明。
- 未启用的可选身份或机制。

### 你的视角

包含：

- 当前玩家 id。
- 当前玩家身份。
- 当前玩家阵营。
- 当前角色基础玩法；默认已经包含身份目标、局势判断、话语权动作、身份姿态选择和条件性身份扮演建议。
- 进阶模式开启时的当前角色进阶玩法，用于追加更细的节奏控制、保护、误导和刺杀判断。
- 当前身份合法可见的额外信息。
- 公开玩家 id 列表。

不同身份的额外信息不同：

- 梅林：可见非莫德雷德坏人玩家。
- 派西维尔：可见梅林候选，候选中包含梅林和莫甘娜。
- 坏人：可见坏人同伴；奥伯伦不参与坏人互认。
- 崔斯坦/伊索尔德：可互相确认对方为好人。
- 普通忠臣：无额外隐藏信息。

### 动作 JSON 格式声明

`【动作 JSON 格式声明】` 提前声明整局常用动作的输出格式，后续行动请求不重复声明这些 JSON 契约。当前固定声明：

- `propose_team`。
- `speak`。
- `vote`。
- `mission_action`。

`assassinate` 和 `use_lady_of_lake` 不放入固定声明。只有实际轮到刺杀或湖中仙女行动时，才在 `【本次行动】` 中临时补充本次 JSON 格式。

### 活动日志

活动日志按事件时间顺序追加，只保留正常玩家能看到且有决策价值的信息：

- 组队：队长和车队成员。
- 发言：玩家 id 和公开发言文本。
- 投票结果：车队是否通过，具体谁赞成、谁反对。
- 任务结果：成功/失败，以及成功票、失败票数量。
- 湖中仙女：公开展示谁查看了谁；若是当前玩家自己的查验，则额外展示查验结果。
- 刺杀：刺客目标和结算后的胜者。
- AI 行动确认：当前玩家自己的行动完成后记录为“已进行处理”。

活动日志不展示技术事件类型前缀，例如 `SPEECH:`、`TEAM_PROPOSED:`；也不展示单个玩家“已完成投票”“已提交任务行动”这类过程噪音。未结算投票不会公开票型；结算后才展示具体赞成/反对玩家。

### 本次行动

`【本次行动】` 只说明本次要执行什么动作、当前可选参数，以及必要时的临时 JSON 格式。常用动作的 JSON 契约已经在 `【动作 JSON 格式声明】` 中提前声明，不在每次行动里重复。

- 组队：返回车队、公开组队理由和私下判断摘要。
- 发言：返回公开发言和私下判断摘要。
- 投票：返回 `approve` 或 `reject`，不需要公开理由。
- 任务：坏人可选择成功/失败；好人任务行动由后端直接提交成功，不请求模型。
- 刺杀：返回刺杀目标、候选排序和私下判断摘要。
- 湖中仙女：返回查验目标和私下判断摘要。

行动提示会引导模型先判断当前阶段的局势目标和身份姿态，再通过具体话语权动作推进局面，例如争取上车、要求换人、质疑身份叙事、保护或拆解某个玩家、逼问矛盾、解释票型和复盘任务压力。组队阶段会要求队伍能被公开记录解释，避免直接把私有身份视角翻译成突兀的最优车；特别是梅林不能连续按隐藏真相精准排除坏人，而要在任务成功、公开理由可信和刺杀风险之间取平衡。梅林在首轮和第二轮公开信息不足时，不应把“避开全部已知坏人”作为默认组队原则；当公开强共识正在保一个梅林私下不放心的人时，不应每次亲手拆掉，非决胜轮必须优先考虑至少一种隐藏方案：把他作为压力位/试车位暂时保留、让别人带这条线自己观察票型、自己不上车改用投票施压，或等他露出公开矛盾后再拆；在非决胜轮、公开证据不足或已经连续正确排人时，可以保留公开记录较强的争议位、扶持别人带正确方向，或把判断包装成试车/压票，而不是每次提交私下最优车；组队的 `private_reason_summary` 也应评估是否过于精准、是否会让刺客锁定自己。`prompt.v12` 会在组队、发言和投票阶段强调身份叙事债：如果动作牵涉梅林候选、疑似派西维尔或保护线，模型需要说明自己站哪条候选线、拆哪条候选线、反跳谁、逼问谁在保护谁，或失败后先追哪条线。`prompt.v13` 则处理 DS 样例暴露的问题：当模型私下已经在判断候选、公开却没人开身份线时，第二轮起也要用公开车队、票型或任务结果包装，轻开一条身份线；可选动作是软保一人、拆一条保护关系、逼问某人为什么急着排/保某人，或把候选压力转成车位压力；同时禁止直接说候选身份，禁止把两个真实候选公开绑定成一组。`prompt.v14` 要求轻开身份线必须通过可说出口的短句落地，避免模型只在私下理由中分析候选。`prompt.v15` 继续要求模型用自己的话完成动作，不要复读示例句，并压制“责任链清晰”“这条线我先记着”“后续再看”等新模板。`prompt.v16` 要求如果 `private_reason_summary` 提到候选关系如何影响本轮态度，`public_message` 必须落一个不泄露的动作，不能只公开说车队结构。发言阶段会显式要求即使首轮也要点名车队中的至少一人、一个被排除的人，或一个替代车位诉求，少用“信息少、希望任务顺利、先观察”这类安全祝愿句，改用更短的桌面口吻直接保人、拆人或追问。在梅林候选/派西维尔叙事、争车位、保护强势好人、压制可疑领队或拆身份叙事时，优先评估是否借派西维尔姿态；如果活动日志已经出现派西维尔、候选、保护、挡刀、假身份或装派西维尔等身份叙事，`public_message` 必须至少有一句主动处理这条叙事，可以半跳、假装保护、反跳、拆穿、把自己放到保护/挡刀位，或撤回普通好人位但同时解释自己在保护哪条线。`prompt.v10` 要求派西维尔在真梅林候选被全桌追打时至少做一层保护性混淆，例如同时评价两名候选、提醒坏人诱导刺杀、替候选争取可解释上车，或把自己放进疑似有视角的位置吸刀。`prompt.v11` 进一步要求发言中引用历史票型和言行矛盾前必须核对活动日志。身份姿态不能只出现在 `private_reason_summary`；公开发言要直接让其他玩家听出你是在保护、拆解、反跳、挡刀或借派西维尔姿态争解释权，但不要自称“我是保护位/挡刀位”。佯装视角可以半真半假地露出方向感，但必须可否认，不能硬报未公开候选名单、验人结果、真实阵营或任务牌提交内容。任务失败后的公开发言不要说自己提交了成功或没有出失败票；改用“从我的立场我不认这张锅”“同车其他人需要解释”“这辆车的组队逻辑需要复盘”。公开话术少用身份标签，多用动作和限定词；不要把任务说成验人，也不要空口保证自己是好人。投票阶段要求票型和最近公开发言保持可解释一致，避免“刚说反对却投赞成”或“刚说支持却投反对”的断裂。任务行动阶段要求坏人在好人已有两次成功、当前任务失败即可阻止刺杀阶段、且车上坏人数量足以达到失败票要求时，默认优先提交失败；只有能说明刺杀胜率明显更高时才继续隐藏。刺杀阶段要求候选排序能排除至少两个其他目标，提高刺杀理由可审计性。身份扮演是条件性策略，不是每轮机械跳身份；如果暂时不公开扮演身份，也应是有意隐藏，而不是忘记争夺身份话语权。行动提示只影响模型表达与策略倾向，不改变后端规则判定。

`prompt.v17` 针对 DS 小样本里“私下提到候选，公开只说这条线我先保着”的问题，把身份动作进一步收紧到玩家或公开行为：公开动作必须点出至少一名玩家、一个保护/排除动作或一段可见互动，例如“玩家X一直替玩家Y卸压”“玩家X急着排玩家Y”“我偏保玩家X这轮上车”。只说“这条线我先保着/认着/记着”会被视为新的模板风险，而不是合格的身份争夺。

补充口语化约束：组队说明和公开发言不能停在抽象试车。`prompt.v18` 要求组队说明必须点名当前车成员、被排除者或失败后先问谁，并带条件、风险或责任顺序。`prompt.v19` 进一步把这条改成正向桌面格式：带上谁是因为他能吃什么压力，没带谁是要他解释哪段关系，车炸了先问谁。`prompt.v24` 增加组队套话自检：如果 `public_message` 仍出现“先跑一轮”“看看结果”“后续再调整”，要求删掉重写成带谁、为什么带、暂时不带谁、炸了先问谁。跨 seed 样本发现组队阶段仍会写“看看反应”，`prompt.v26` 将它并入组队套话自检。`prompt.v27` 增加首轮泛话自检，要求“先走一车”“希望任务顺利”“信息少”改成点名被排除者、替代车位诉求或失败责任。v27 复测里组队说明仍出现“先走一车”，`prompt.v28` 将它也并入组队套话自检。v28 跨 seed 仍出现“先走一车试试”“后续再看”，`prompt.v29` 将这两类话提升到全局套话约束，同时保留正向替代：直接点名谁没上车、谁要解释、失败后先问谁。v29 清除了模板短语，但样本出现“我没出失败票”这类用私下任务牌自证的发言，`prompt.v30` 继续要求任务失败后只能用公开立场和同车责任施压，不能声称自己提交了成功票。v30 子代理审阅后指出“认这张底牌”“打这张任务牌”仍把成功任务说得过硬，`prompt.v31` 因此补充：成功任务不是验人，公开表达应改成“暂时认一轮”“先不急拆”“看他怎么接压力”。v31 样本又暴露真派把两名候选一起带上车、一起证明、一起解释的刺客可读风险，`prompt.v32` 因此要求候选回扣优先单点玩家或单段关系，另一名候选留到投票或下一轮再压。v32 样本继续出现“看看结果”“接受检验”“任务理由”“投出失败”等模板感或验人感话术，`prompt.v33` 将它们改写成单候选车位压力：上车吃压力、这车炸了先解释车位和投票立场、或队长说明为什么把某人排除在外。多样本和子代理审阅进一步指出，继续堆禁句会鼓励模型绕词表，`prompt.v34` 因此转向动作分流：同一轮已有玩家追问排除点后，后续发言要换成争车位、要求换人、条件票、归责排序、拆保护关系或质疑谁在借排除点带票；刺客和莫甘娜也要用假保护、拆线或转移压力参与身份叙事，而不是中立复读。v33/v34 多样本还暴露“唯一赞成/唯一反对”这类票型事实误读，`prompt.v35` 因此要求引用唯一票、孤立票前必须核对活动日志中的公开投票结果；没有把握时改成追问，不能把多人同票说成某人唯一投票。v35 多 seed 复测显示，仅要求“核对”仍不足，模型会继续口误成唯一票；`prompt.v36` 因此转成结构化动作：说唯一票前先读赞成名单和反对名单，若多人同票就说“反对之一/赞成之一”；派西维尔候选回扣按“一个玩家、一个公开动作、一个桌面要求”落地；任务失败只按车队成员、组队理由、投票结果和发言矛盾排责任，不能用自己的任务牌证明谁坏。v36 seed33 继续围绕错误“唯一反对”展开，说明仍缺少生成前事实 grounding；`prompt.v37` 进一步要求凡是 public_message 要用上一轮、首轮、唯一票、反对者或赞成者支撑判断，private_reason_summary 必须先列出对应轮次的赞成/反对名单；同时要求候选上车压力必须公开说成“玩家X上车吃压力，这车炸了先解释上车前后的态度”，避免只在私下观察任务结果。公开发言建议控制在 1 到 3 句；如果一句话能压到具体玩家，就不写成长段复盘。

`scripts/prompt_log_evaluator.py` 提供样本质量门槛：样本至少 12 个 AI 决策、至少 1 个公开身份争夺动作、至少 1 个候选关系压力动作、私下候选关系影响必须全部转成候选关系压力、不能出现公开候选绑定风险、不能出现模板短语，不能用私下任务牌自证，不能把成功任务说成过硬的身份确认，不能把两名候选同时放进公开试验框架，也不能出现“接受检验”“任务理由”“投出失败”这类把任务说成验人的话术；当样本内已有完整投票决策时，也会抓取“某人唯一赞成/唯一反对”与实际赞反票不符的公开事实误读。v16/v17/v18 的当前样本仍未通过该门槛；v18 retry 首条组队仍出现模板短语。v19 清除了该模板短语，但样本中派西维尔仍把私下候选判断公开成“关注玩家怎么接局势”，没有转成保人、拆关系、逼问或车位压力。`prompt.v20` 因此补充：观察候选反应不是公开动作，必须改成可被全桌回应的压力，例如让某人上车吃压力、某人这轮先别被打死、追问谁为什么急着排某人，或说明失败后先问谁。子代理审阅 v20 样本后指出：玩家4 的车位压力有进步，但主要压在非候选玩家3上，仍不是真正的候选解释权争夺。`prompt.v21` 因此要求真派私下因候选改变判断时，公开优先追候选本人，或追谁在推、保、拆候选；只压无候选关系的玩家不算完成。`prompt.v22` 进一步处理短样本退化，把“多一个视角”“观察一轮”“看看反应”列为模板风险，并给出更口语的替代：问候选领队为什么把某人排在外面，或问某人为什么把另一名玩家往车上推。v22 样本经过评估器补充后能识别“跳过/留在外面”这类自然说法，但仍暴露出首条派西维尔候选判断转成普通车位压力的问题；`prompt.v23` 因此加入候选回扣自检：私下理由一旦用到候选，公开句必须点到候选本人，或点到推、保、排、跳过候选的人，否则先重写公开句。v24 样本继续暴露首轮派西维尔被候选领队带上车时只说信任和配合的问题；`prompt.v25` 增加首轮候选回扣，要求候选领队带你、排掉另一候选，或公开选择信任某候选时，至少问一句可公开解释的问题。v33 评估器同时补充自然单候选压力识别：例如“为什么把玩家X排除在外”“这车失败，玩家X请解释”“带玩家X上车，炸了先解释车位和投票立场”，但仍不会把没有车位或失败上下文的泛泛“玩家X请解释”算作候选压力。v36 评估器补充两处结构修正：承认“候选被排除在外，对这车怎么看”这类自然追问是候选关系压力；解析“玩家A说带唯一反对的玩家B”时抓被修饰的玩家B，避免把前文玩家A误当成唯一票对象。

发言阶段的 `stance` 不是必需字段；解析层会在缺省时按 `uncertain` 处理。

## 角色与身份提示

角色基础文案分为三层：

- `role_descriptions`：本局配置中的身份机制和基本可见事实。
- `role_gameplay`：玩家视角中的默认角色玩法，包含身份目标、局势判断、身份姿态选择、话语权动作和条件性身份扮演建议。
- `role_strategy_tips`：玩家视角中的角色进阶玩法，只在进阶模式开启时展示，用于补充更细的节奏控制、隐藏/误导/保护和刺杀判断。

这些文案会按当前玩家身份展示，不会把其他玩家的隐藏身份真相暴露给当前玩家。

当前默认策略会强化不同身份的桌面打法差异：

- 好人会主动争夺可信话语权，围绕上车/下车、票型、任务结果和身份叙事逼出更多公开信息，并选择普通好人、可信上车位、强势推理位、保护位、派西维尔姿态或挡刀位等身份姿态。
- 梅林会用公开逻辑引导正确车队，通常扮演普通忠臣、谨慎推理位或愿意上车的好人，必要时短暂借用派西维尔姿态制造候选迷雾；组队前会检查队伍是否能被公开记录解释，避免连续按隐藏真相精准排除坏人，或让组队、投票和发言长期呈现同一条精准排雷线。非决胜轮可以保留可解释的不完美，例如跟随部分公开共识、放进公开记录较强的争议位，或扶持其他好人领队来降低梅林感。当已知坏人在车上时，不能只用“隐藏身份所以支持”，而要选择软反对、结构性质疑、条件支持、替代车或失败后归责预案等可否认动作。
- 派西维尔会在辨别梅林/莫甘娜时制造保护性模糊，必要时公开或半公开扮演派西维尔、反跳假派西维尔、扮演保护位或挡刀位，但避免过早卖出候选关系；每次私下理由需要说明候选关系如何影响本轮态度，公开发言至少体现保护、混淆或观察候选反应中的一种。`prompt.v12` 强化“半藏半露地抢候选解释权”：真派应点名一条要保的线、一条要拆的线，或逼问谁在借候选关系带票。`prompt.v13` 要求第二轮还没人谈候选时，派西维尔也要用公开车队或票型包装，轻开一条身份线，但不说候选身份、不公开绑定两个真实候选。`prompt.v15` 要求轻开身份线时用自己的话完成动作，避免把示例句变成新模板。`prompt.v16` 要求私下因为候选关系改变态度时，公开必须用不泄露身份的动作表达一部分。`prompt.v19` 补充真人局边界：真派不要报拇指，而是用逻辑、车位、投票和候选反应收集信息；遇到抢跳时先判断对方是在挡刀还是抢解释权。`prompt.v20` 进一步要求“观察候选”必须落成桌面压力，不能只说自己关注谁。`prompt.v21` 要求这类压力优先落到候选本人，或落到推、保、拆候选的人身上，避免真派只去压一个与候选关系无关的普通车位玩家。`prompt.v22` 明确：当候选领队排掉另一候选时，优先追问领队为什么排他，而不是只申请自己上车。`prompt.v23` 要求每次涉及候选都做候选回扣自检，公开句必须点到候选本人，或点到推、保、排、跳过候选的人。`prompt.v25` 把首轮候选领队带人也纳入回扣，避免真派只说信任和配合。当某个候选因持续纠偏被集火时，不应简单跟压，而应通过候选双评、挡刀、吸收视角嫌疑或拆刺客诱导来保护候选空间。
- `prompt.v17` 要求派西维尔的公开保护/拆解必须落到玩家或公开行为上，不能只说“这条线我先保着”；这能把候选判断转成真人桌上能听见、但仍可否认的争夺动作。
- 忠臣会更主动地要位置、逼解释、建立信任链；在争上车、保护强势好人、压制可疑领队、拆身份叙事或给疑似梅林挡刀时，可短暂假装派西维尔、反跳假派西维尔、反压假派西维尔、轻开身份线或挡刀，但不能把猜测说成验人。
- 坏人会主动选择假身份姿态，尤其可扮演假派西维尔来误导候选关系、保护错误对象、逼真视角露头或质疑真视角；刺客会逼真派西维尔或挡刀忠臣表态，莫甘娜会假装懂候选关系来诱导派西维尔站错线，并可在无人开身份线时主动开一条假的保护线或错误质疑线。坏人同时避免固定每次强冲或每次出失败票。支持含坏人的车时，需要预埋后续叙事钩子，例如谁承担组队责任、失败后优先压谁、自己为什么仍可信，或下一轮换掉哪个位置。
- 关键任务中的坏人会优先考虑任务胜利路径：当好人已有两次成功且当前失败能阻止第三次成功时，如果车上坏人数量足以满足失败票需求，默认应出失败并准备推锅，而不是无条件隐藏到刺杀。
- 奥伯伦这类无互认坏人在候选叙事已触发时，默认要参与身份争夺，优先用保护位或假派西维尔姿态搅混候选关系，而不是只用“信息少、先观察”退出讨论。
- 刺客会结合跳身份、挡刀、被保护关系和任务纠偏记录判断谁最像梅林。

当前覆盖身份包括：

- 亚瑟的忠臣 / 忠臣。
- 梅林。
- 派西维尔。
- 刺客。
- 莫甘娜。
- 莫德雷德。
- 奥伯伦。
- 爪牙。
- 崔斯坦。

## 进阶模式开关

配置项：

```json
"role_tip_detail": {
  "enabled": false,
  "label": "进阶模式",
  "role_tips": {}
}
```

默认关闭。关闭时，模型仍会收到增强后的角色基础玩法，包括身份目标、局势推进、身份姿态选择、话语权动作和条件性身份扮演。

打开后，会在当前玩家自己的角色基础玩法后追加角色进阶玩法，例如更细的发言节奏、隐藏方式、误导方式、保护方式、刺杀判断方式等。模型不会看到 `role_tip_detail`、`enabled` 等配置键名。

进阶模式适合用于：

- 进一步细化角色扮演节奏和风险控制。
- 增强不同身份在压力局、关键票型和终局刺杀前的发言差异。
- 让模型更接近玩家攻略中的常见打法，而不是承担默认角色扮演的全部责任。

进阶玩法不适合写入：

- 配置说明。
- “默认开启/关闭”之类元信息。
- 当前玩家不应知道的隐藏身份真相。
- 与当前身份无关的其它身份私密策略。

## 可选机制

配置项 `optional_mechanics` 用于描述可开关机制的文案。机制是否进入模型输入由每局 `enabled_options` 决定。

当前包含：

- 湖中仙女：仅 8-10 人局可开启；第 2、3、4 次任务结算后，持有者查看一名从未持有过湖女的玩家阵营，并转交湖女。
- 崔斯坦：和伊索尔德互相确认对方是好人。
- 伊索尔德：和崔斯坦互相确认对方是好人。

只有启用后的机制才进入 `【本局配置】`。未启用机制不会显示给模型，避免模型把未生效规则当成当前对局事实。

湖女查验结果属于执行查验玩家的合法私有信息，只会出现在该玩家后续 prompt 的 `【你的视角】` 或 `【活动日志】` 中，不进入其他玩家视角。活动日志对其他玩家只展示“谁使用湖女查看了谁”，不展示阵营。

## 推荐身份组合

`recommended_role_setups` 保留为 prompt 配置中的参考信息，但当前建局规则使用后端规则层固化的 5-10 人推荐身份组合。该字段不作为运行时规则裁判来源。

该字段不直接发送给模型。模型只需要知道“本局实际身份”，不需要知道推荐表、默认表或配置来源。

当前规则层只允许 9-10 人局开启崔斯坦/伊索尔德，开启后由后端把两个忠臣替换为这对身份。

## 元信息禁止进入模型输入

以下内容不应出现在最终发给模型的 prompt 中：

- 提示词版本号。
- 配置文件路径。
- 配置键名。
- `enabled`、`default_enabled_for_player_counts` 等开关字段。
- `recommended_role_setups` 或“推荐身份组合”。
- “默认不加入推荐身份组合”。
- “可选扩展身份”等配置性质描述。
- 原始 JSON 上下文字段名。

如果需要记录这些信息，应保存在 AI 决策日志或配置文件中，而不是发送给模型。

## 相关代码

- `backend/app/services/game_service.py`：在对局推进中触发 AI 行动，保存 AI 决策日志和 `prompt_messages`。
- `backend/app/ai/player.py`：AI 决策调用链；`AiPlayer._decide()` 负责构造上下文、拼接 prompt、调用模型、解析输出并记录 token/cache usage。
- `backend/app/ai/context.py`：构造 `AiContext`、`stable_prefix`、`stable_prefix_hash`、动态上下文和当前阶段合法动作。
- `backend/app/prompting/templates.py`：最终 prompt 拼接入口；`PromptBuilder.build_messages()` 生成模型 `messages`，同文件负责玩家视角、固定动作格式声明、活动日志、本次行动和事件文本渲染。
- `backend/app/prompting/config.py`：加载和校验 `prompt_templates.json`。
- `backend/app/prompting/schemas.py`：解析和校验模型 JSON 输出，非法输出会交由后端规则校验或触发 AI 决策错误。
- `backend/app/llm/provider.py`：把 `messages` 放入 OpenAI-compatible Chat Completions 请求体，并读取 token 与缓存命中用量。
- `config.example/prompt_templates.json`：可提交的默认提示词文案、角色标签、事件模板和动作输出契约。

## 维护建议

- 修改提示词展示结构时，优先检查最终生成的 `prompt_messages`，不要只看配置文件。
- 修改文案、角色标签、事件模板或动作输出契约时，优先看 `config.example/prompt_templates.json`。
- 修改拼接顺序、消息 role、玩家视角、活动日志或本次行动格式时，优先看 `backend/app/prompting/templates.py` 和 `backend/app/ai/context.py`。
- 稳定前缀只放固定系统规则和本局固定配置；玩家身份视角、公开事件历史、当前阶段、合法动作等动态内容必须放在 system message 之后。
- 当前“增量”优化指让每次请求的前文保持一致，并让活动日志按事件时间顺序追加，避免重排、合并改写旧记录或重复声明常用动作 JSON 格式；OpenAI-compatible Chat Completions 仍然是无状态请求，不应假设 API 只接收 delta 或自动记住上一轮上下文。
- `assassinate` 和 `use_lady_of_lake` 不应进入固定动作 JSON 声明，只在实际请求对应行动时临时声明。
- 需要排查缓存效果时，看 AI 决策日志中的 `stable_prefix_hash`、`prompt_tokens`、`cached_tokens` 和 `cache_hit_rate`。
- 增加角色时，至少补齐身份标签、机制说明、玩法、策略、合法视角规则。
- 增加开关时，区分“配置给系统看的内容”和“模型需要知道的游戏事实”。
- 测试应优先覆盖长期行为，例如合法视角、不泄露原始 JSON、投票和任务结果可读，以及目标、上车/下车、质疑/反跳、合法信息边界等行为关键词簇，而不是绑定某一句攻略文案。
